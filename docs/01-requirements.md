# 01 · 需求、目标与成功标准

## 1. 用户与场景

- **主要用户**：公司员工（含实习生、正式员工）。他们在报销、假期、差旅、信息安全、采购等制度问题上，
  以及产品会员/导出/退款等 FAQ 问题上，需要一个**能指出出处的答案**。
- **次要用户**：制度归口部门（HR / 财务 / 行政）。他们关心的是：Agent 不会替员工"选一个"看起来方便的解释，
  冲突时会回到制度管理流程。
- **典型交互**：一次性提问，或带上下文的追问（"那要提前几天申请？"）。

## 2. 目标

1. 回答必须**可核验**：给出文档 ID、章节、逐字原文；答案中的每个数字都能在引用原文里找到。
2. **冲突不擅断**：两份制度对同一事项给出不同取值、且没有适用范围/优先级依据时，列出双方原值与引用并请求确认。
3. **资料不足就说不足**：知识库没有依据时返回明确状态与资料缺口，而不是用常识补全。
4. **过程可审计**：每一步动作、参数、观察摘要、决策依据都可回放（trace.jsonl）。

## 3. 范围

**做**：
- 合成制度/FAQ 语料（13 份，带文档 ID、版本、生效日期、适用范围）；
- 文档检索（`search_docs`）、原文读取（`read_doc`）、取值一致性核查（`check_consistency`）三个工具；
- ReAct 循环：模型选动作 → 执行 → 观察 → 调整下一步或结束；
- 步数 / 工具调用上限与明确的未完成状态；
- 引用校验（逐字匹配 + 数字溯源）与答案组装；
- 离线 Mock 规划器 + OpenAI 兼容的真实模型规划器；
- 7 组运行材料（正常 / 冲突 / 资料外 / 改写 / 追问 / 工具失败可恢复 / 工具失败不可恢复）。

**不做**（明确排除）：
- Web 界面、线上部署、多 Agent 协作、生产级 Runtime；
- 权限体系（谁能看哪份制度）、真实文档接入（Confluence/飞书）、向量数据库；
- 多轮会话存储（`history` 由调用方传入）。

## 4. 成功标准（对应题目验收点）

| # | 验收点 | 判定标准 | 证据 |
| --- | --- | --- | --- |
| A1 | 明确答案 | `status=answered`，引用逐字存在于原文，数字可在引用中找到 | `examples/case1_clear_answer` |
| A2 | 文档冲突 | 两个取值都列出、都有引用；不给单一结论；`status=needs_clarification` | `examples/case2_doc_conflict` |
| A3 | 资料外问题 | `status=insufficient_info`，`answer=null`，`gaps` 非空，无引用 | `examples/case3_out_of_scope` |
| A4 | 改写后的相似问题 | 与标准问法命中同一文档、给出同一结论 | `examples/case4_paraphrase` |
| A5 | 上下文追问 | 仅凭当前问题无法定位文档，结合历史后命中正确文档 | `examples/case5_followup` |
| A6 | 工具失败 | 可恢复时换策略重试；不可恢复时 `status=failed` 且不输出答案 | `examples/case6_tool_failure_recover`、`case7_tool_failure_terminal` |
| A7 | 动态决策 | 同一问题在"只有一篇文档"与"两篇冲突"环境下动作序列不同 | `tests/test_robustness.py` |
| A8 | 执行上限 | 触达步数/工具调用上限返回 `incomplete` | `tests/test_agent_paths.py::test_limits_return_incomplete` |

## 5. 非目标层面的取舍

题目说"界面、线上部署、多 Agent、生产级 Runtime 均非必需"，因此本项目把有限的时间预算全部投入
**检索质量 + 冲突处理 + 引用可核验性**这三件审核要点上，其余一律从简（CLI、单进程、本地文件语料）。
